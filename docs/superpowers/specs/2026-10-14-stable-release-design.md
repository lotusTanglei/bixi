# Bixi 首个生产稳定版发行设计

> 状态：对话中的发行边界已获确认；本书面规格待复核。本文不是已通过验收或已发布的声明。
>
> 盘点基线：2026-10-14 的 `main` / `origin/main`，提交 `51cd48e`。发行候选提交将在阻断修复后重新冻结。
>
> 目标版本：`v1.0.0`。正式标签只在全部发行门禁通过后创建。

## 目标与边界

首个稳定版面向单机部署的实际使用者。它保证当前产品已提供的功能在启用时可用、可维护、可恢复，并且同一业务实现可在 cloud 和 single 运行。发行范围是现有功能的收口，不以三阶段路线图中尚未实现的移动端、支付、K8s、多节点高可用等项目作为完成条件。单机稳定版不宣称多节点容灾或未经测量的吞吐量与 SLA。

本版只支持**空库全新安装**。开发期数据库没有正式版本基线，不承诺从 `51cd48e` 或更早提交原地升级。现有库不应运行全量初始化 SQL；安装入口必须在执行前拒绝非空目标库。`v1.0.0` 成为未来稳定版升级路径的起点。

个人电脑仅执行串行、低负载的静态检查与功能回归。需要独立环境的恢复、故障和有界容量验证不得在个人电脑上进行高强度压测。

## 受支持的部署矩阵

| 编号 | 交付方式 | 模式 | 发行验收环境 |
| --- | --- | --- | --- |
| D-C | Docker Compose | cloud | Ubuntu 24.04 LTS x86_64、Docker 24+、Compose v2 的参考宿主机 |
| D-S | Docker Compose | single | 与 D-C 相同的参考宿主机 |
| N24-C | 原生 JAR + Nginx | cloud | Ubuntu 24.04 LTS x86_64、Java 17、systemd、Nginx |
| N24-S | 原生 JAR + Nginx | single | 与 N24-C 相同的系统基线 |

这四项分别留证，不以一个模式、操作系统或交付方式的结果代替另一项。Compose 的 Ubuntu 24.04 是本版认证宿主机；其他宿主系统即使能够运行 Compose，也不列为已认证环境。原生部署的参考验收全程不使用 Docker；MySQL、Redis、Nacos、RabbitMQ 和需要时的 S3 兼容存储由原生安装或外部托管服务提供。single 需要 MySQL、Redis；cloud 另需 Nacos、RabbitMQ。所有中间件的实际版本与连接方式写入发行清单，不把任意版本的兼容性当作已验证事实。

> 2026-11-10 调整：v1.0.0 的发行验收矩阵由六项收缩为四项（D-C、D-S、N24-C、N24-S），Ubuntu 22.04 的原生验收暂不纳入本版，列为后续补测项。保留两个维度不变——交付方式（Compose / 原生）与部署模式（cloud / single），只收敛操作系统版本，理由是操作系统版本主要影响打包而非业务代码路径。

## 功能契约

发行前建立一份唯一的能力总账，以当前用户可到达的页面、API、配置开关和部署入口为准，逐项覆盖 Auth、UPMS、Demo Task、验收资源、Generator、Quartz、站内通知及已提供的外部渠道、AI、Workflow、Monitor、文件能力。每项记录启用条件、外部依赖、权限与租户边界、审计要求、四项环境中适用的结果和证据。Monitor 等只在特定模式提供的能力，其他环境须写明不适用的架构原因；已对外声明支持的能力不能标为不适用。源码目录、依赖或未暴露的路线图方案本身不算已交付功能。

默认关闭的现有功能必须同时验证关闭态不会泄漏入口、开启态能完成真实业务流程。AI 模型、对象存储和外部通知等依赖供应商的能力需要在受控测试账号或等价真实服务上验证请求、失败和恢复；缺少凭据时记为阻断，不把模拟器通过写成真实送达。公开文档、菜单和配置不得声称未验收的能力可用。

统一 HTTP 验收脚本可利用 `BIXI_ENV_FILE`、`BIXI_ORIGIN` 和 `BIXI_API_BASE_URL` 连接 Compose 或原生服务，业务断言不按交付方式复制。浏览器、进程管理、中间件配置和数据恢复属于交付方式专项验收。

## 制品与生产配置

从一个冻结的候选提交生成并归档 cloud JAR、single JAR、对应的两套前端构建、Compose 应用镜像、SQL、生产配置模板和操作说明。发行清单记录提交、统一版本号、文件 SHA-256 与镜像摘要。已有 CI 的 JAR 校验可复用；前端与镜像需补齐版本绑定。四项环境安装与验收必须使用待发布的原样制品，不能在目标机临时从源码重建后借用验收结果。

前端公开资源不得包含 OAuth 客户端密钥、`BIXI_ENCODE_KEY` 或其他服务端密钥。认证与报文保护的改动须保持登录、刷新、权限和失败响应契约，并完成密钥轮换。生产凭据只通过受保护的运行时配置注入；cloud 不沿用 `dev` Nacos 配置作为生产交付。原生部署交付受控环境文件、systemd 服务定义和 Nginx 配置，验证 HTTPS、上游地址、健康检查、开机自启、停止、重启及日志读取。Compose 同样使用受控凭据和固定镜像摘要。

## 数据与恢复

在每种模式和交付方式完成空库初始化、运行时密钥写入、登录与核心数据读写。空库检查必须在包含 `DROP TABLE` 的初始化 SQL 之前运行，且拒绝非空库时不得修改已有数据。对创建失败和部分初始化的情况提供明确的清理及重试步骤，仅允许对可丢弃的新库重建。

发行后数据保护至少覆盖 MySQL 与启用的对象存储：在隔离环境备份一份有实际业务记录的数据库及对象，恢复到新实例，以同版本制品验证登录、权限、文件和业务记录。记录恢复步骤、实际耗时、数据核对结果及可恢复到的时间点。首版无旧稳定版可回退，因此不演练开发期数据库反向迁移；首次空库安装失败时只清理可丢弃的新库，同版本重部署失败时先保留现有数据，再按最近一致备份和实际写入情况决定恢复，不能用安装前的空库备份覆盖业务数据，也不能以 `make reset` 代替恢复。

## 验收与退出门禁

每个候选提交依次通过架构/配置检查、双模后端与前端构建、相关模块测试、四项部署启动与统一功能黑盒、权限/租户/审计负向用例、真实浏览器检查、启用功能专项、空库安装、备份恢复和运维演练。专用环境中每项部署再以两个并发会话连续运行核心 HTTP 路径 15 分钟，要求无未解释的 5xx、进程退出或内存溢出，并记录响应时间和资源占用；该轻负载检查不构成更高吞吐量的承诺。既有 [黑盒计划](../../../.docs/BLACKBOX_TEST_PLAN.md) 的 BB-09 至 BB-12、BB-15 至 BB-16 必须纳入本版，旧 `PASS` 只作为历史线索。候选提交变化后重跑受影响用例及发行总门禁。

能力总账的状态只用 `PLANNED`、`IMPLEMENTED_UNVERIFIED`、`BLOCKED`、`PASS`、`NOT_APPLICABLE`、`OUT_OF_SCOPE`。`PASS` 必须包含候选提交、制品摘要、环境编号、用例、预期/实际结果、时间和可复现证据。`NOT_APPLICABLE` 必须写明该功能为何不属于该模式。缺陷记录复现输入、影响级别、修复提交和复验结果。未实现且不公开提供的路线图项目才可标为 `OUT_OF_SCOPE`；已提供功能不能靠这两种状态规避验收。

冻结候选提交时先将 Maven 与前端版本统一为 `1.0.0`，再构建、验收并归档该版本的制品。正式发行条件是：四项环境均 `PASS`，每项发行能力在适用环境中均 `PASS`，不适用项均有可核对的模式原因；无未解决的安全、数据损坏、越权或核心功能缺陷，安装/恢复证据完整，文档与实际制品一致。只有此时才基于已验收提交创建 `v1.0.0` 标签、推送并发布 GitHub Release；发行说明列出支持环境、启用前置条件、已验证限制和制品摘要。

## 开发闭环与当前阻断

实施按五个可独立验收的切片推进：范围总账冻结；安全及生产配置；不可变制品与原生部署；四项环境功能和浏览器验收；数据恢复与发行。每个切片先固定用例与退出条件，再修复该切片阻断，记录证据后关闭；新发现的缺陷进入总账，不暗中扩大功能范围。阶段完成不以代码存在、编译通过或历史百分比判断。

当前盘点已经发现以下发行阻断，状态均为未关闭：

- Compose 和原生前端构建把服务端 OAuth 密钥及加密键放入公开 JS；
- 原生部署只有手工 JAR 步骤，缺少 systemd/Nginx 生产模板与实测；cloud 原生默认使用 `dev` 配置，AI 网关 profile 亦未在直装步骤中闭环；
- CI 已校验后端 JAR，但前端、镜像和四项环境尚未证明使用同一组待发布制品；
- 当前项目总账仅覆盖旧提交的两个资源，黑盒计划仍有低权限、双租户、导入边界和浏览器待测项；
- 空库安全检查、真实恢复及同版本重部署缺少发行证据。

本规格冻结发行契约，不预先宣称上述阻断已修复，也不授权在验收前打稳定版标签。
