# Bixi Skills 技能套件设计

> 2026-09-21 完整性复核修订。本文是实现规格；验收条目均是未来交付条件，不代表五个技能已经实现或验证。对应[开发计划](../plans/2026-09-21-bixi-skills-implementation.md)。

## 目标

为 Bixi 建立一套可通过 `npx skills` 安装、供 Codex、Claude Code 等编程 Agent 使用的项目技能套件。技能套件帮助 Agent 理解 Bixi 的双模架构和开发约束，按统一流程完成开发、调试、架构审查与验证。

第一版只新增 Agent 技能包，不新增 Bixi 后端接口、数据库表、前端菜单或运行时依赖。

## 需求边界

### 已确认需求

- 技能名称使用以下五个名称：
  - `bixi-context`
  - `bixi-feature`
  - `bixi-debug`
  - `bixi-architecture`
  - `bixi-verify`
- 技能包使用标准 `skills/<skill-name>/SKILL.md` 布局。
- 技能既支持显式命令，也支持基于 `description` 的自然语言触发。
- Bixi 仓库存在 `.codegraph/` 时，代码定位必须优先使用 CodeGraph。
- 技能必须遵守 `AGENTS.md`、`.docs/1_ARCHITECTURE.md` 和 `.docs/5_AI_DEVELOPMENT.md`。
- 技能不得修改 `.docs/.chiwen.state.json`，不得提交 `.env`、凭据、构建产物或个人绝对路径。
- Bixi cloud 与 single 必须复用同一套业务实现。

### 非目标

- 不实现 PIG 的远程文档搜索服务或 `pig`/`ai` 搜索索引。
- 不把技能包装成 Bixi 产品内的 AI 菜单、REST API 或数据库能力。
- 技能调用本身不授权提交、合并或发布；遵循本次任务已有授权，不为已授权操作重复询问。
- 不用技能替代 Bixi 现有代码生成器；`bixi-feature` 可以调用并审查生成器结果。
- 不增加 Bixi 运行时依赖；包维护校验使用已有 Node.js 18+ 内置模块，安装使用版本固定的 `skills` CLI。

## 技能包结构

第一版在当前仓库顶层 `skills/` 维护技能源代码，作为独立于业务模块的可安装包。这是本版落地选择；尚未创建或发布独立远程仓库。后续拆仓时应同时迁移技能、校验器和评测资料，并保留对目标 Bixi 仓库的外部引用。

```text
skills/
├── README.md
├── bixi-context/
│   └── SKILL.md
├── bixi-feature/
│   └── SKILL.md
├── bixi-debug/
│   └── SKILL.md
├── bixi-architecture/
│   └── SKILL.md
├── bixi-verify/
│   └── SKILL.md
└── evals/
    ├── README.md
    ├── context-search.md
    ├── feature-crud.md
    ├── debug-regression.md
    ├── architecture-boundary.md
    └── dual-mode-verification.md

scripts/
├── validate-skills.mjs
└── validate-skills.test.mjs
```

每个 Skill 必须自包含触发条件、操作步骤、输出格式、停止条件和 Bixi 约束。Skill 不复制整份架构文档，而是引用仓库内的权威文件和具体示例路径。

### 安装与目标仓库定位

- 五个技能可单独安装，不依赖同级技能、`skills/README.md`、评测文件或维护脚本被一起复制。维护脚本只由套件开发者使用。
- 从用户当前项目或明确指定的项目路径定位 Bixi 根目录，使用 `git rev-parse --show-toplevel`，并核对 `AGENTS.md`、`pom.xml`、`bixi-module/` 和 `bixi-ui/`。所有项目路径相对此根目录解析，不能从技能安装目录寻找业务代码。
- 非 Bixi 仓库、缺少必需材料或多个候选仓库且无法确定时，说明缺失信息；已知项目路径则直接继续，不搜索整个用户目录。
- 目录中的 `name` 是稳定标识。Codex 显式调用使用 `$bixi-context` 等名称；Claude Code 使用 `/bixi-context` 等名称，实际发现与调用需在客户端验收。自然语言触发属于模型行为，不能用文件安装成功代替验证。
- README 提供可执行的本地源安装：`npx --yes skills@1.7.0 add . --skill bixi-context --agent codex --copy -y`（从 Bixi 根目录执行）。远程安装只在真实地址已发布并验证后说明，不使用可误执行的仓库地址占位符。

### 触发与协作边界

| 用户目标 | 主技能 | 协作方式 |
| --- | --- | --- |
| 查询实现位置、解释现有机制 | `bixi-context` | 只读；不因提到 CRUD 自动开发 |
| 新增或扩展功能 | `bixi-feature` | 自行完成上下文、边界检查及验证；其他技能可选 |
| 复现并修复已有缺陷 | `bixi-debug` | 即使需要改代码也保持缺陷范围 |
| 明确要求架构审查、拆分服务评估 | `bixi-architecture` | 审查与建议；实施遵循用户任务范围 |
| 执行检查、评价是否可交付 | `bixi-verify` | 汇总真实结果；发现失败不自动展开无关重构 |

复合任务由用户主要目标选主技能，按需读取其他已安装技能，不递归相互调用、不自动派生 Agent。交接信息包含：目标、Bixi 根目录、改动文件、已知证据、已运行命令、未完成项；不重复用户已回答的问题或已经完成且仍有效的检查。

## 共同运行契约

所有技能遵循以下顺序：

1. 确认用户目标、影响范围和是否需要修改文件。
2. 检查当前工作区状态，保留用户已有改动。
3. 若存在 `.codegraph/`，先运行 `codegraph explore` 获取符号、源码和调用路径。
4. 再读取与问题相关的架构文档、模块 README、SQL 和前端参考实现。
5. 明确证据、假设、待确认事项和预计修改文件。
6. 完成任务后只报告实际执行过的命令和结果。

不存在 `.codegraph/` 时直接跳过，不能自动建立索引；存在索引但工具执行失败时，保留错误并回退 `rg` 和定向文件读取。CodeGraph 返回的当前源码不再重复读取。技能输出默认使用中文，用户使用其他语言时跟随用户语言。

用户本次指令及目标仓库的适用约定优先于技能默认流程。现有实现必须以当前源码核实，文档与源码冲突时同时标明约束与现状；不能把未提交改动视为已发布版本。部署模块列表可能演进，技能不得固化旧版本的 Workflow、AI 等单体支持状态。

## 技能设计

### `bixi-context`

职责是为后续开发提供项目上下文，不直接修改业务代码。

- 触发：查询 Bixi 架构、模块职责、示例实现、权限、SQL、部署、调用链或“这段代码在哪里”。
- 入口：显式选择 `bixi-context`，按客户端使用 `$` 或 `/`。
- 检索顺序：CodeGraph → `.docs/1_ARCHITECTURE.md` → `.docs/5_AI_DEVELOPMENT.md` → 目标模块 README → 定向源码和 SQL。
- 输出：结论、证据文件与行号、调用关系、相关命令、限制或未找到项。
- 禁止：只凭训练记忆回答项目事实；把搜索结果当作已经验证的运行结果；修改文件。

### `bixi-feature`

职责是实现完整的 Bixi 业务功能，参考 `bixi-module/bixi-upms-biz/src/main/java/com/lotus/bixi/upms/demo` 和 `bixi-ui/src/views/demo/task`。

- 触发：新增业务域、CRUD、后台页面、接口、菜单或数据库表。
- 入口：显式选择 `bixi-feature`，按客户端使用 `$` 或 `/`。
- 必须检查：模块归属、API/biz 边界、Entity、DTO/VO、Mapper、Service、Controller、分页、详情、Jakarta Validation、权限、操作日志、三类 SQL、前端 API/页面/表单/权限/状态、测试和双模验收。
- 权限：查询使用 `<domain>_<resource>_view`，新增/修改/删除分别使用 `add/edit/del`；写操作使用稳定的 `@SysLog` 标题。
- 双模：只维护一份业务实现；跨模块调用使用 `*-api/service` 传输无关接口，cloud 使用 Feign，single 使用本地适配器。
- 输出：先列修改清单和验证计划，再实施；完成后列出文件、测试结果和未执行项。
- 生成器：先核实模板可用性，再由 Agent 审查输出；生成器模板缺失时按真实参考实现开发，不把生成器当必需前置。
- 行为验收：将新业务真实 CRUD、非法请求、未授权/已授权请求及持久化操作日志检查加入 `scripts/acceptance.mjs`，由两种部署运行同一用例。仅检查注解存在不能证明权限生效。

### `bixi-debug`

职责是以最小回归测试为起点处理缺陷。

- 触发：报错、接口异常、权限错误、cloud/single 行为不一致、测试失败或性能异常。
- 入口：显式选择 `bixi-debug`，按客户端使用 `$` 或 `/`。
- 流程：复现 → CodeGraph 追踪入口和调用方 → 判断影响范围 → 写失败回归测试 → 最小修复 → 受影响模块测试 → 双模验证。
- 必须检查：是否同时影响 cloud 与 single，是否涉及 Feign/本地适配器，是否存在权限和审计遗漏。
- 禁止：在没有复现或回归测试证据时宣称修复；通过部署模式特判或 localhost Feign 回环绕过问题。
- 已有回归测试能暴露问题时复用该测试，不为形式重复写测试；无法复现时只报告调查证据、候选原因和未验证项。

### `bixi-architecture`

职责是审查模块边界和部署模式一致性，不承担业务实现。

- 触发：架构审查、依赖调整、服务拆分、Feign 改动、模块迁移或“是否违反架构”。
- 入口：显式选择 `bixi-architecture`，按客户端使用 `$` 或 `/`。
- 检查项：`deployment -> biz -> api/common` 方向、`common` 是否依赖 `*-biz`、`*-api` 是否包含实现、消费者是否依赖传输无关接口、cloud/single 适配器是否正确、是否有重复业务代码、localhost Feign 回环、权限和 SQL 契约是否完整。
- 输出：按严重程度列出问题，包含文件/行号、违约规则、影响和最小修复建议；无问题时列出已检查范围。
- 末尾检查：`make architecture-check`，并报告实际结果。

### `bixi-verify`

职责是根据改动范围执行质量门禁并给出可审计结果。

- 触发：验证改动、准备提交、准备合并、交付前检查或“测试是否完整”。
- 入口：显式选择 `bixi-verify`，按客户端使用 `$` 或 `/`。
- 选择命令：
  - 模块/API/依赖变化：`make architecture-check`、`make runtime-config-check`、对应 cloud/single CI。
  - 后端行为变化：`make backend-cloud-ci`、`make backend-single-ci`。
  - 前端变化：`make frontend-ci`。
  - 共享行为变化：`make verify-cloud`、`make verify-single`。
  - 仅技能/文档变更：套件静态检查、安装与场景评测；不宣称已完成业务运行验收。
  - 最终通用检查：存在 `.codegraph/` 时 `codegraph sync .`，以及 `git diff --check`。
- 输出：检查项、实际命令、结果、失败原因、未执行项、已知限制和是否满足交付标准。
- 禁止：把“计划执行”写成“已通过”；隐藏失败命令；修改用户未授权的配置或凭据。
- 环境前置：Java 17、Maven、Node、Docker/Compose 和本地配置按目标任务核对。服务未启动时必须先 `make start-cloud` 或 `make start-single`；同一环境按 cloud 验收后再切换 single，不能同时构建/切换两种模式。
- 隔离：检查当前服务和端口，不停止其他任务的部署。当前 `scripts/bixi.sh` 的启动流程会输出初始凭据，启动日志必须保存到权限受限的本地文件，只展示脱敏后的结果。缺环境时标记“阻塞/未执行”，不能跳过后给总体通过结论。

验证结果契约：`检查项 | 适用原因 | 命令 | 工作目录 | 模式 | 退出码 | 状态 | 脱敏证据位置`。状态只有通过、失败、未执行、阻塞、不适用；所有必需项通过才可宣称任务验收通过。

## 交互和安全策略

- 多个子系统按依赖拆为工作项；上下文可确定的模块、名称和验证命令由 Agent 决定。
- 只有缺失信息会改变任务结果且无法合理推断时才提问；等待时继续独立工作。
- 遵循当前授权，普通修复和可逆文件变更不增加审批；未获授权的外部发布、合并或破坏性操作才需要确认。
- 运行命令时不得打印 `.env` 或其他敏感配置内容。
- 技能必须保留工作区已有改动，不执行无关格式化或全仓库重构。

## 验收设计

### 静态验收

- 五个目录均包含有效 YAML frontmatter 和非空正文。本包使用两行双引号标量的受限格式（`name`、`description`），便于无额外依赖校验；不声称实现完整 YAML 解析器。
- 名称、目录和 README 中的安装命令一致。
- 校验已登记的 Bixi 参考路径与 Make 目标确实存在；人工检查新增引用及描述的语义。关键词正则不能证明没有触发冲突。
- 允许写“不得修改 `.docs/.chiwen.state.json`”和“不要输出 `.env`”；禁止的是读取后输出秘密、修改受保护状态或携带个人绝对路径，不是禁止文件名本身出现。
- 校验器聚合错误，以非零退出码报告失败；需有正常包、缺文件、错误名称、空描述、失效路径、失效命令、保护说明不误报等测试。

### 场景验收

每个技能有正常、边界、反向触发三类场景，共 15 个场景，具体输入和断言见开发计划 Task 8。先在未加载技能时记录基线，再用同一模型、同一 Bixi 快照和提示词评测；每次新会话，避免先前答案污染。

- 上下文检索：找到 `demo/task` 后端、SQL、权限、日志、测试和前端链路；没有索引时不自动建索引；普通 Java 问题不误触发。
- 新增业务：除方案清单外，在一次性 Bixi 副本真实完成一个 CRUD，运行构建和两种模式的同一黑盒用例，检查权限拒绝与审计日志；源工作区仅交付技能与脱敏记录。
- 缺陷修复：在副本注入可复现的权限名错误，保留原测试，记录失败到通过；不能只列修复建议就记为修复完成。
- 架构审查：识别 `api -> biz`、single Feign 回环和重复 Controller；不把合法的云/单体适配选择判成违规。
- 验证报告：混合通过、失败、缺环境和不适用时仍准确汇报；未经执行不能伪造退出码或日志。

每条场景都记录客户端/模型版本、源码提交、技能摘要、提示词、实际输出、工具记录及逐项结果。已通过的基线不虚构为失败。静态通过、安装通过、行为通过分别统计；任一必需场景未跑完，则技能包不能标记为完整验收。

安装验收覆盖五个技能与 Codex/Claude Code 两个客户端目标，共 10 次独立安装；只安装一个技能时应可完成其工作，不因缺少另外四个技能而报错。安装文件落盘与客户端实际能调用是两个验收项。

### Bixi 仓库验收

- `make architecture-check` 通过。
- `codegraph sync .` 通过。
- `git diff --check` 通过。
- 技能包静态检查和安装冒烟测试通过。
- 不修改 Bixi 运行时模块和用户维护的生成状态文件。

## 分阶段交付

1. 第一阶段：创建包布局、README、五个 `SKILL.md` 和静态检查脚本。
2. 第二阶段：补充五组场景评测文件，完成 10 次独立安装和客户端调用验证。
3. 第三阶段：运行 Bixi 仓库门禁，修正文档和触发冲突，形成首个可发布版本。

后续独立发布不属于第一版验收。本次修订仅完善设计和计划，不提前执行 Skill 实现或业务场景评测。
