# Bixi 路线图

## 项目定位

Bixi 是面向独立开发者和中小团队的现代 Java 企业开发平台，以单体与微服务双模架构为主体，提供适合 AI 辅助开发的工程结构、开发规范和自动验证能力。

核心原则：

- 微服务模式是新用户默认入口，单体模式是轻量部署选项。
- 两种模式共享同一套业务实现，不复制 Controller、Service、Mapper 或前端页面。
- 权限、工作流、AI、OSS、定时任务和监控等能力保持开源。
- 所有完成项必须有可运行入口、自动测试和对应文档，不能只以代码存在作为完成依据。

### 版本与兼容性原则

- Bixi 是开源项目，当前开发不承担早期版本 API、数据库表结构、前端请求或历史配置的兼容承诺。
- 允许删除兼容层、重命名接口、重建表结构、重做 DTO 和前端页面，优先选择干净、可维护、可验证的设计。
- 当前基线以干净环境初始化和双模验收为主要依据；未来确有数据保护需求时，再单独提供一次性迁移脚本。
- 不为了兼容旧实现保留错误接口、重复模型或已经失效的工作流/生成器契约。

## 三阶段总览（重新制定：2026-09-21）

三阶段按能力依赖推进，不按白皮书功能数量平均分配。核心依赖链是：**双模工程底座 → 身份/权限/数据治理 → 生成器与业务闭环 → 生态扩展与生产治理**。后一个阶段不应建立在前一个阶段尚未验证的权限、租户和审计规则之上。

| 阶段 | 定位 | 当前状态 | 主要结果 |
| --- | --- | --- | --- |
| 第一阶段 | 可信基础与安全数据底座 | 工程基线已完成；安全、租户和数据权限仍未完成 | 两种部署模式在可靠身份、权限、审计和数据隔离下运行 |
| 第二阶段 | 高效交付与核心业务闭环 | 待实施 | 从干净数据库生成可用业务，并让工作流、通知、调度、文件和 AI 形成可验收闭环 |
| 第三阶段 | 开放生态与生产平台 | 待实施 | 提供移动/微信/支付/报表等方案，并具备可扩展、可观测、可发布的生产能力 |

每个阶段都必须同时交付代码、SQL、前端入口、配置、测试、文档和双模验收。依赖或页面存在不算完成；静态核查发现的问题必须转化为可重复的正向和负向用例。

## 第一阶段：可信基础与安全数据底座

**阶段目标：** 在已有双模工程基线之上，建立所有后续模块共用的身份、权限、审计、租户和数据访问规则。工程基线（cloud/single 启动、统一业务实现、Compose、CI、基础示例）保持回归，不重复建设。

**第一阶段 A：认证、授权与审计。** 修正并验证 cloud/single 的登录参数校验、Token 生命周期、方法级权限、授权缓存失效、短信发送、密码策略、失败锁定、SSO 回调和异步审计主体。社交登录只在核心认证契约稳定后接入，不为保留旧接口增加兼容层。

**第一阶段 B：租户与数据权限。** 建立可信租户上下文、MyBatis 行隔离、Redis 键隔离、租户开户/切换/停用和可信身份来源；实现组织 DataScope、字段脱敏、敏感词和报文加密。所有规则必须覆盖列表、详情、导出、写操作、缓存、文件和异步任务。

**第一阶段 C：共享安全基础设施。** 收口通用幂等、私密文件授权、对象与数据库失败补偿、动态数据源的最小业务场景，并让日志、异常和接口文档遵守权限与脱敏规则。

第一阶段退出条件：

- cloud 和 single 分别通过错误密码、缺失/篡改认证参数、未登录、低权限、Token 过期/撤销和非法回调的拒绝测试。
- 用户、角色、菜单、按钮、日志、导出和详情接口均有服务端方法级权限；授权变更在已有会话中按规则生效。
- 两个租户的同名账号、列表、详情、写入、导出、Redis、文件和异步任务完全隔离，租户不能由请求参数伪造。
- DataScope 和字段脱敏由服务端统一执行，不能通过修改 `deptId`、分页或导出参数绕过。
- 验收脚本、后端测试、双模构建、`make architecture-check` 和运行配置检查全部通过。

## 第二阶段：高效交付与核心业务闭环

**阶段目标：** 让开发者从干净安装生成一个遵守第一阶段安全规则的业务模块，并把已有高级模块变成真实可用的业务能力。

**第二阶段 A：全栈生成与开发模板。** 恢复可用默认模板，完成 CRUD、父子表、导入导出、API/biz 输出、权限/菜单/审计产物、模板预览、输出路径校验和双模编译；模板市场先固定版本和失败回滚，社区模板扩展留到第三阶段。

**第二阶段 B：工作流与办公闭环。** 统一流程 key、定义 ID、任务 ID、意见字段和表单 schema 契约；打通表单设计、版本、字段权限、BPMN 部署、流程发起、待办/已办、审批结果回写和通知。按专项计划继续实现幂等、可靠重试、集群恢复，再评估会签、加签、延时、HTTP 触发器、催办和打印归档。

**第二阶段 C：现有模块和工程生产力。** 完善站内/多渠道通知、Quartz 真实执行结果、SBA 监控、接口文档、数据库重建/迁移工具、生产配置和 CI 制品流程；完成 AI 模型配置、PDF/Word 解析、分块、Embedding、选库、引用、会话历史和所有者权限闭环。

第二阶段退出条件：

- 新建干净数据库后，一张主表和一组父子表可生成、编译、启动，并在 cloud/single 通过页面、权限、审计和 CRUD 验收。
- 工作流完成“发起→待办→通过/拒绝→历史→业务单状态”，重复提交、异常重试、服务重启和越权处理均有确定结果。
- Quartz 长任务不重叠，HTTP 500 和 JAR 非零退出记为失败；通知发送状态、重试和 SSE 重连可追踪。
- AI 文档可正确摄取并被选定知识库召回，回答带可追溯来源，跨用户/租户文档不能进入上下文。
- 高级模块可独立启停，不影响核心系统；双模构建、前端检查、运行验收和模块专项测试全部通过。

## 第三阶段：开放生态与生产平台

**阶段目标：** 在安全底座和核心业务闭环稳定后，建设可按项目选配的行业能力与生产治理，不把 PIG 白皮书中的可选组件误当作核心完成条件。

**第三阶段 A：业务生态方案。** 按真实需求建设移动 H5/App/小程序、移动 CMS、微信公众号、支付收单、站点统计、JimuReport 报表和 GoView 大屏；每个方案都要有身份回调、租户/权限、状态机、异常补偿和独立验收。

**第三阶段 B：生产平台和规模能力。** 建设 XXL-JOB/ElasticJob 适配、动态路由、限流/熔断、灰度发布、K8s/Rancher/Helm/HPA、SkyWalking、ELK、读写分离、分库分表、Seata、信创兼容矩阵和完整 DevOps 晋级回滚。

**第三阶段 C：社区扩展机制。** 固化模块 SPI、工程构建器、模板市场贡献流程、机器可读架构元数据、版本发布和性能/安全基准。稳定版本内部提供迁移工具和升级路径，但不对当前早期版本承担兼容承诺。

第三阶段退出条件：

- 每个启用的生态模块都有从配置、菜单、权限到业务回调/发布/对账的真实闭环；未启用模块不会改变核心系统启动。
- 生产部署可以重复完成多实例发布、探针检查、扩缩、灰度、故障恢复和回滚，并保留制品与审计记录。
- 跨服务请求可以关联 trace、日志和业务对象；集中日志有脱敏、保留期、租户过滤和告警策略。
- 至少一组目标数据库、信创环境和规模场景完成初始化、迁移、权限、业务和性能回归，而不是只验证连接成功。
- 社区模块可按扩展契约接入 cloud/single，架构检查和安全基线不会被绕过。

## PIG 商业版功能逐项对比与阶段归属（2026-09-21 补充）

对照来源：[PIG CLOUD 商业版白皮书 V6.1](https://paper.pig4cloud.com/)。PIG 一侧只按白皮书公开文字记录，未获得商业源码、完整演示环境或运行验收结果；“PIG 可选”表示白皮书明确为可选模块，“PIG 仅声明”表示只有宣传/方案描述，不能据此推断默认交付。Bixi 一侧依据 2026-09-21 对源码、SQL、前端、配置、部署文件和已有测试的静态核查；执行前仍须复核当前代码和运行证据。

状态含义：**已有**=有实现入口且与当前架构一致；**部分**=核心片段存在但缺少一个或多个交付环节；**链路断开**=前后端、配置、存储或业务回写无法形成完整链路；**未发现**=本次仓库核查没有找到对应交付物；**待验证**=静态上有入口，但缺少双模/故障/安全运行证据；**PIG 可选**和**PIG 仅声明**只描述对照侧，不代表 Bixi 状态。

## 当前开工点：第一阶段 A 的认证与权限闭环

下一步从**认证契约和权限边界**开始，不从报表、移动端或支付开始，也不先扩展生成器。生成器和工作流会复制权限、租户和审计规则；这些底座未定版，越早生成越容易形成二次返工。

第一个开发批次按以下顺序执行：

1. **先复现并固化测试。** 对 cloud 和 single 分别测试 `/token/form` 的缺失参数、错误密码、非法 `grant_type`、篡改认证字段、Token 过期/撤销和退出后的访问；对用户、角色、菜单、日志的 page/detail/export/写接口用低权限账号直接请求。静态疑点必须先变成可重复测试，不能凭代码阅读直接下结论。
2. **修正权限边界。** 给缺少方法级权限的读接口补上权限声明和负向测试；修复授权缓存失效参数错误，覆盖新增授权、撤回部分、撤回全部和已有会话；统一 cloud/single 的本地与 Feign 认证上下文。
3. **接通安全认证配套。** 在短信供应商接入前先定义验证码发送、TTL、限频、复用和失败接口契约，开发环境使用可观测的测试发送器但不把验证码放入响应；随后补密码强度、强制改密和失败锁定。
4. **补齐可信审计。** 为成功、拒绝、异常和异步写入记录操作者、对象、结果和请求关联；异步任务显式传递安全主体，不读取请求线程残留身份。
5. **双模收口。** 同一组正向/负向测试分别跑 Gateway/cloud 和 single，执行相关后端测试、`make backend-cloud-ci`、`make backend-single-ci`、`make frontend-ci`、`make verify-cloud` 和 `make verify-single`；全部通过后才进入第一阶段 B 的租户与数据权限。

本批次明确不做报表、大屏、移动端、支付和完整 K8s；也不为了历史版本兼容保留已经证明错误的请求字段或工作流契约。完成标准是安全边界可运行、可测试、可重复，而不是新增了多少页面或依赖。

以上阶段安排是新的开发计划；PIG 对比表中的状态仍是当前核查结论，只有完成对应退出条件并取得运行证据后才更新为“已有”。
