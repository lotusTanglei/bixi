# Bixi 路线图

## 项目定位

Bixi 是面向独立开发者和中小团队的现代 Java 企业开发平台，以单体与微服务双模架构为主体，提供适合 AI 辅助开发的工程结构、开发规范和自动验证能力。

核心原则：

- 微服务模式是新用户默认入口，单体模式是轻量部署选项。
- 两种模式共享同一套业务实现，不复制 Controller、Service、Mapper 或前端页面。
- 权限、工作流、AI、OSS、定时任务和监控等能力保持开源。
- 所有完成项必须有可运行入口、自动测试和对应文档，不能只以代码存在作为完成依据。

### 第一阶段验证基线

2026-08-25 已完成以下可重复验证：

- `make verify-cloud` 与 `make verify-single`：同一黑盒脚本通过登录、用户信息、菜单、权限、示例任务 CRUD、异常响应和操作日志验收。
- `make backend-cloud-ci` 与 `make backend-single-ci`：两种 Maven Profile 的完整构建和测试通过。
- `make frontend-ci`：前端依赖安装、ESLint 和生产构建通过。
- `make runtime-config-check`、`make architecture-check` 与 `make doctor`：运行时配置、架构规则和本机环境检查通过。

阶段中的“新用户 30 分钟启动”和“1 小时借助 AI 完成业务模块”属于使用时效指标，仍需通过真实新用户演练持续采样；不影响上述工程退出条件已经满足。

## 第一阶段执行顺序

### 1. 固化双模边界

- 将模块标记为基础模块、业务 API、业务实现、独立应用或部署聚合模块。
- 约束依赖方向：应用/聚合模块 -> 业务实现 -> 业务 API/公共模块；公共模块不得依赖业务实现。
- 为跨模块能力定义与传输方式无关的业务接口。
- 微服务模式使用 Feign 适配器，单体模式使用本地实现；禁止在单体中新增本机 HTTP 回环调用。
- 为依赖方向和两种适配器选择增加自动测试。

### 2. 建立默认微服务启动入口

- 提供版本固定的 Compose 基础设施和服务编排。
- 将 Nacos Data ID 配置纳入可审查的项目资产，并支持环境变量覆盖敏感值。
- 提供 `doctor`、`start`、`status`、`logs` 和 `stop` 入口。
- 默认启动最小闭环：MySQL、Redis、Nacos、Gateway、Auth、UPMS；RabbitMQ、MinIO、AI、Workflow、Quartz、Monitor 按明确策略启用。

### 3. 完成单体启动闭环

- 为单体提供与微服务一致的环境检查和数据库初始化入口。
- 明确 AI、Workflow、Monitor 在单体中的聚合或外置策略。
- 验证登录、用户、角色、菜单、权限和操作日志基础闭环。

### 4. 建立标准示例和统一验收

- 选择一个独立业务域作为示例，不使用系统管理表冒充业务示例。
- 用环境变量切换验收基地址，不复制测试代码。
- 验收至少覆盖建表、CRUD、菜单可见性、按钮权限、操作日志和异常响应。

### 5. 收紧持续集成门禁

- 保持 `make backend-cloud-ci` 与 `make backend-single-ci` 都通过。
- 将统一黑盒验收分别指向 Gateway 和 Single 入口。
- 加入数据库脚本全链路执行、前端静态检查和生产构建。

### 6. 完善 AI 开发上下文

- 在架构文档维护模块职责、依赖规则、双模调用规则和验证命令。
- 每个任务模板要求 AI 先定位业务归属，再修改同一套业务代码，最后执行双模门禁。
- 文档只记录当前仓库可验证事实；计划能力留在本路线图，不写成已实现能力。

### 7. 发布稳定基线

- 清理默认密码、个人绝对路径、废弃配置和不再成立的文档。
- 冻结数据库初始化顺序和配置兼容策略。
- 完成第一阶段所有退出条件后再创建稳定版本标签。

## 阶段验收

- 新用户在 30 分钟内启动默认微服务模式，并通过 Gateway 访问系统。
- 单体模式可独立启动，并通过与微服务相同的核心功能验收。
- 同一业务模块不复制代码即可在两种模式运行。
- 两种模式的构建、核心测试和示例验收均自动执行。
- 新用户在 1 小时内借助仓库内 AI 上下文完成一个标准业务模块，并通过双模门禁。

## 后续阶段

- 第二阶段：完善代码生成、可选高级模块、升级迁移、可观测性和 AI 任务模板，形成高效开发体验。
- 第三阶段：建立稳定版本、扩展机制、行业方案、机器可读架构元数据，以及性能、安全和可靠性基准。
