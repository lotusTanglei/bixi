# Bixi Flowable 工作流双模落地开发提示词

状态：开发任务说明，尚未执行开发或验收。

关联：[[开源/bixi/三阶段计划]]、[[开源/bixi/当前进度]]。

使用方式：在 Bixi **代码仓库**中开启编程会话，将下面整段提示词交给开发 Agent。知识库仅保存任务说明；实现、开发清单、ADR 和验收证据写入代码仓库的约定位置。可分多轮执行，后续会话先读取已落盘的进度再继续。

## 可直接复制的开发提示词

```text
你是 Bixi 项目的架构与开发负责人。请基于仓库实际代码，分阶段完善 Flowable 工作流模块，使其成为按需启用、支持单体与微服务双模、支持多实例部署和跨服务可靠协作的企业审批能力。

一、确定的选型与任务边界

1. 继续使用 Flowable，不替换引擎，不引入第二套引擎。此前核查版本为 7.1.0，以仓库实际依赖为准；本任务不默认升级引擎。若存在阻塞性兼容问题，先给出证据和最小调整方案。
2. 主场景为人工审批、工单和业务流转，同时支持流程中的跨服务自动任务。
3. 单体与微服务两种模式必须从第一阶段共同实现和验证，不能先完成微服务再将单体兼容留到最后。
4. 同一个业务模块维护唯一一套 Controller、Service、Mapper、实体、状态机和前端实现；部署入口只负责组合与装配。
5. 优先复用已有 Java、Spring Boot、MySQL、RabbitMQ、安全、日志和配置组件。
6. 不实现通用多引擎平台、自研调度器或完整低代码平台。可视化设计器不作为第一阶段前置条件。
7. 外部副作用按可能重复执行设计，以持久化状态、至少一次投递、幂等、补偿和对账实现可靠业务效果。
8. 不覆盖用户未提交修改，不自动提交、推送或部署到外部环境。

二、先核查仓库并建立开发清单

1. 阅读 AGENTS.md、架构文档、开发规范、发布基线及验收脚本。存在 .codegraph 时，先使用 CodeGraph 定位代码与调用关系。
2. 检查工作流依赖、自动配置、数据源、事务管理器、监听器、API、业务实现、数据库表及前端页面。
3. 检查 cloud/single Profile、应用启动类、组件扫描、Feign、本地适配、Nacos、网关、配置加载与可选模块机制。
4. 检查消息封装、数据库迁移及测试实际覆盖；区分“已实现且验证”“有代码但未验证”“未实现”。
5. 重新核实此前发现的线索：
   - Workflow 尚未纳入 single 聚合及默认运行验收。
   - 流程发起缺少完整请求幂等。
   - 流程结束监听主要更新本地工作流记录，可靠跨服务通知需要补齐。
   - 部分 Workflow 测试 mock 被测服务本身，不能验证真实实现。
   - workflow.enabled 是否真正阻止引擎、执行器和业务组件启动，需要检查。
6. 在代码仓库约定位置记录差距清单、架构决策、分阶段任务和验收矩阵；这些线索不能未经核查直接认定为现状。
7. 核查完成后按顺序开发。每阶段达到验收条件后继续；普通实现选择自行解决并记录理由。环境阻塞时准确记录并继续可独立完成的工作。

三、双模架构硬性要求

1. 模块边界：
   - workflow-api：传输无关业务契约、DTO、结果及事件契约；远程适配遵循仓库结构。
   - workflow-biz：唯一工作流业务实现，封装 Flowable。
   - common-workflow：公共引擎配置与基础支持，不反向依赖业务模块。
   - 示例业务依赖工作流业务契约，不直接使用 Flowable API，也不直接访问 ACT_* 表。
   - 不让两个业务模块互相依赖实现类；回调使用契约及部署模式对应适配器。
2. cloud 模式：
   - Workflow 作为独立服务，支持多个副本共享工作流数据库。
   - 同步请求使用统一契约的远程适配，服务发现、认证和路由复用 Bixi 现有机制。
   - 跨服务可靠命令及结果事件使用持久化 Outbox 和 RabbitMQ 适配。
3. single 模式：
   - 将同一套 workflow-biz 按需聚合进 bixi-single，不要求额外启动 Workflow 服务。
   - 跨模块同步调用使用本地适配；不注册无用 Feign 客户端，不调用 localhost HTTP。
   - 不依赖 Gateway 或 Nacos；工作流审批及内部异步闭环不强制依赖 RabbitMQ。
   - 内部可靠异步事件使用同一套持久化事件契约和本地投递适配，重启后能够补偿处理。
   - 不以普通内存事件、线程池队列或仅 AFTER_COMMIT 回调充当可靠投递；这些机制至多用于唤醒持久化投递器。
4. 同步调用适配与可靠事件适配分别设计，保持实现最小化。共用事件处理器和业务规则，不复制两套审批逻辑。
5. 两种模式保持一致的业务状态、权限、接口契约及最终结果；可以有不同事务边界，但不能让业务正确性依赖 single 特有的大事务。
6. 工作流内部 Flowable 状态、工作流扩展表、Outbox 写入应加入同一本地事务，必须验证实际数据源和事务管理器。跨模块或跨服务流程不要默认获得全局事务。
7. 业务状态与命令持久化、消费去重与业务更新分别在各自本地事务中完成；不使用跨服务长事务包裹整段流程。
8. 应用启动类、组件扫描、Bean 选择和条件配置必须避免引擎重复创建、同名 Bean、循环依赖与 cloud 配置泄漏至 single。
9. 工作流启用/关闭策略覆盖后端、引擎、执行器、事件处理、路由、菜单和前端入口。关闭后核心系统正常，原有流程数据保留；重新启用可恢复待处理工作，不能偷偷消费或确认未处理事件。
10. 支持同一套代码在两种模式部署。已有数据的模式迁移必须单独说明停机、配置、数据库与消息处理步骤；不能将“支持双模”描述为可随意热切换。

四、阶段一：双模可选装配与真实审批闭环

目标：在 single 和 cloud 下使用同一套示例完成发起、审批和业务结果回写。

功能点：
1. 补齐双模模块装配、业务契约、本地/远程适配及功能开关，保持既有依赖方向。
2. 建立独立请假申请示例：草稿、提交、详情、列表、流程发起、待办、已办、审批通过、拒绝结束、审批历史、业务状态回写。
3. 明确业务状态与流程状态映射、合法转换及终态。区分拒绝结束与退回修改，第一阶段先完成拒绝结束。
4. 提供可重复部署的 BPMN 文件、基础部署入口、菜单和权限数据；第一阶段不要求完整流程设计器。
5. 实现申请、待办、已办、详情及审批记录页面，共用 API 契约和前端实现。
6. 校验办理资格及数据权限，不能仅依靠按钮权限。租户体系如已存在，贯穿部署、发起、查询及办理；不自行扩展一套新租户平台。
7. 提供启用及禁用的配置示例、启动命令与诊断入口。
8. 建立真实引擎集成测试及双模黑盒验收；不得以 mock 被测服务本身代替测试。

验收：
- single 启用：没有 Gateway、Nacos、独立 Workflow 服务时完成审批闭环；工作流不要求 RabbitMQ。
- cloud 启用：通过正常网关/服务调用链完成相同业务流程。
- single/cloud 禁用：核心验收通过，不创建引擎或后台执行器，不出现失效菜单和无条件依赖。
- 非办理人、越权查询和非法状态转换得到明确响应。
- 阶段一仅表示基础闭环完成，跨服务故障可靠性须经阶段二验收后才能宣称具备。

五、阶段二：双模一致的幂等与可靠协作

目标：无论本地还是远程传输，请求重试、宕机和消息重复后都能恢复正确结果。

功能点：
1. 发起幂等：稳定请求标识、数据库唯一约束、请求内容冲突检测、已有结果查询。区分同一请求重试和业务重新申请轮次。
2. 任务操作幂等：保存必要命令及结果，同一任务并发审批只产生一次有效转换；重复请求返回稳定结果。
3. 核实工作流内部事务，审核异常捕获、监听器错误及状态同步，避免吞异常造成部分提交。测试同步结束流程和普通人工流程的记录创建/结束时序。
4. 优先复用可靠消息基础；不足时补最小 Outbox。事件携带 eventId、类型、schemaVersion、流程实例、业务标识、申请轮次及必要追踪上下文。
5. Outbox 支持持久化重试、退避、多实例安全领取及过期恢复，处理发送成功但未标记完成的窗口。
6. cloud 投递器使用 RabbitMQ，处理发布确认、不可路由、消费确认与失败重投。消费者去重记录与业务更新同事务提交，提交后确认消费。
7. single 投递器调用共用本地事件处理器，处理器成功提交后再标记交付完成；执行后标记前宕机允许重试，由相同去重逻辑保证正确。
8. 通过事件版本、申请轮次与合法状态转换处理乱序、过期和重复消息。不得把去重仅放在 MQ 适配层。
9. 业务提交与发起工作流之间也需持久化可靠命令或等效可恢复机制，避免业务提交成功而流程永远未启动。
10. 提供一个“审批后执行自动业务任务”的示例：持久化请求、等待执行结果、关联回传并恢复流程。single 本地处理、cloud 独立业务服务处理，共用业务规则。
11. 明确超时、重试、终止后的迟到结果及业务补偿，外部操作具有幂等标识；补偿也需可重试。
12. 异步执行显式传递操作者、租户及业务上下文，不依赖请求线程的 SecurityContext；授权信息来自可信服务端上下文。
13. 提供失败任务/事件查询、审计、人工重试及对账入口。

验收：
- 发起成功但响应丢失后重试不产生第二个实例。
- 同一任务并发审批、重复命令和结果回传保持结果正确。
- single 本地异步事件在进程重启后继续处理，已处理事件重放无重复副作用。
- cloud 下游暂停、消息重复、确认丢失及乱序均可恢复。
- 数据库提交与投递之间、消费提交与确认之间杀进程，均不丢业务结果。
- 两种模式最终状态及权限语义一致；不要求异步处理耗时完全相同。

六、阶段三：微服务多实例及故障恢复

目标：验证真实 Flowable 集群能力，同时保持单体可运行与重启恢复。

功能点：
1. 提供至少两个 Workflow 副本共享同一工作流数据库的 cloud 配置。
2. 配置执行器、线程池、连接池、任务领取、任务锁、过期回收、重试、退避、实例标识及优雅停机。
3. BPMN 明确异步边界；启用异步执行器不等于所有步骤自动异步。
4. 所有可执行节点具备兼容的流程执行代码与配置，避免某节点领取任务后缺少 Delegate 或监听器。
5. 验证任务锁过期可能造成再次执行，外部副作用始终依赖幂等，不能只依赖锁。
6. 验证 Outbox 多实例领取与消费去重；single 同样完成进程重启、定时任务和异步事件恢复验证。
7. 生产使用受控数据库迁移，避免多个副本启动时无序变更表结构。流程部署支持去重与版本管理。
8. 新流程版本发布后旧实例沿原定义完成；旧执行代码、表单版本和事件契约保持兼容，迁移必须显式执行。
9. 增加任务/事件积压、最老等待时间、重试、死信、执行失败及命令/流程/业务单关联诊断。
10. 提供可重复故障演练脚本。区分应用多副本、数据库高可用和跨地域容灾；不能将单数据库上的演练描述为已验证数据库高可用。

验收：
- cloud 停止一个 Workflow 节点，其他节点继续处理请求。
- 执行异步任务时杀节点，过期任务按配置恢复，业务副作用不重复。
- 定时任务在节点故障后继续推进，多实例竞争不破坏状态。
- single 无外部 MQ 时也能从持久化记录恢复内部异步工作。
- 新旧流程版本并存且旧实例完成。
- 双模开关与核心功能回归通过；记录实测恢复时间和限制。

七、阶段四：审批能力与管理体验扩展

前述阶段稳定后依次完善，每项均覆盖 single/cloud：
1. 候选人、候选组及已有组织角色体系集成。
2. 转办、委派以及委派后的处理闭环。
3. 退回修改、重新提交和撤回。
4. 会签、或签与完成条件。
5. 超时提醒、催办及通知幂等。
6. 表单版本绑定、服务端校验与节点字段权限。
7. 流程轨迹、异常任务和事件投递管理页面。
8. 按已有前端基础完善 BPMN 可视化设计器。

每种操作必须明确适用状态、办理资格、审计以及并行/多实例任务和重试下的语义。不得以任意节点跳转替代通用退回语义。

八、双模验收矩阵与交付标准

必须覆盖四组基础组合：
A. single + workflow enabled：完整审批、内部异步及重启恢复；不依赖 Nacos/Gateway/独立 Workflow/RabbitMQ。
B. single + workflow disabled：核心功能正常，无引擎及工作流后台任务。
C. cloud + workflow enabled：完整审批、跨服务可靠事件及至少两个 Workflow 副本故障恢复。
D. cloud + workflow disabled：核心功能正常，无失效路由/菜单和启动强依赖。

single 的要求限定工作流新增依赖，不随意重构其他既有模块。检查时区分其他模块已经要求的基础设施与工作流引入的依赖，记录实际边界。

1. 共用业务验收场景与断言，按部署模式选择启动及连接配置；不得维护两套逐渐分叉的业务测试。
2. 复用仓库已有 architecture-check、runtime-config-check、backend-cloud-ci、backend-single-ci、frontend-ci、verify-cloud、verify-single 等入口，先核实实际覆盖，再补充工作流验收命令及 CI 作业。
3. Flowable、数据库事务和并发使用真实集成测试；可靠消息使用实际传输及故障注入。可使用 mock 隔离无关外部系统，但不能 mock 被测实现来证明其正确。
4. 环境不可用时列出未执行的测试及原因，不声称通过；完成可独立推进的工作。
5. 每阶段落盘：开发清单、ADR、启停配置、双模使用说明、数据库/流程升级说明、恢复与对账操作、验收证据及已知限制。
6. 模式切换文档明确处理在途命令、Outbox、MQ 积压及消费去重记录，防止本地和远程投递器同时消费同一待投递集合。相同代码可双模部署不代表数据迁移自动完成。
7. 性能测试记录硬件、数据库、流程模型、并发、延迟、错误率及积压；只依据实测讨论容量。
8. 每阶段输出简短报告：完成内容、关键设计、运行命令、验证结果、剩余问题和下一步。后续会话从该记录继续，不重复重建已完成内容。
9. 最终完成标准：一套业务实现与前端，四组启停验收，真实审批示例，双模可靠事件闭环，微服务多实例故障恢复，版本兼容及明确的升级/迁移边界。
```
