## 实施顺序与语义

| 批次 | 实现边界 | 必须证明的行为 |
| --- | --- | --- |
| 4A 候选人/候选组 | 角色 ID 到稳定候选组名的服务端映射，扩展待办/数据范围/认领资格；角色和用户有效性走现有 API 契约与 local/Feign 适配 | 候选用户和组成员均可看见候选任务；非成员不能查询或认领。并发认领一个胜者；认领后仅办理人处理，角色范围不成为越权通道。 |
| 4B 转办/委派 | 在阶段二唯一服务上补齐目标身份有效性和组织约束、审计、前端完整操作；原 owner 与 assignee 各自含义固定 | 转办后原办理人不能继续操作；委派未解决不可审批/再次委派；解决后交回原 owner，再由 owner 审批。失败响应重试仍返回原结果。 |
| 4C 退回/重提/撤回 | 新版本请假 BPMN 包含显式修改任务和返回审批路径；绑定不可变模型版本，使用稳定命令与既有可靠事件 | 退回只允许模型声明的审批到修改路径，申请人在修改任务更新允许字段并重新提交；拒绝仍为终态。重新申请使用新业务轮次，原轮次终态不改写。撤回仅在模型与业务状态允许时生效；进入外部副作用后走阶段二取消/补偿协议。 |
| 4D 会签/或签 | 用 Flowable 多实例 userTask 和受控 completionCondition 实现全员/任一通过，服务端校验非空去重参与人集合 | 每个任务一次有效终结。会签未满足人数不前进；或签达到条件取消剩余任务。剩余任务的旧请求、并行拒绝/取消/完成竞争有确定响应，不重复外部副作用。 |
| 4E 超时/催办 | BPMN 定时节点持久化提醒，提醒通过现有 Outbox/inbox；定义 reminderId、提醒窗口和接收对象，催办接口有间隔约束 | 多节点争抢和重启不重复提醒；已终结任务不继续催办；重试与补偿保留身份。用真实通知接收记录证明结果，不用日志或内存事件代替持久化。 |
| 4F 表单版本/权限 | 发起时绑定已发布 formVersionId，保留旧 schema；节点按绑定版本与服务端权限校验后合并字段 | 新版表单不改变旧实例；必填/类型/长度等服务端校验拒绝坏值；只读/隐藏字段不能被请求覆盖，隐藏字段不出现在响应。表单失败与引擎/扩展/事件整体回滚。 |

## 表单与设计器边界

1. 表单发布使用唯一 `(form_id, version)` 与锁定 form 行分配版本；已发布 schema 不原地修改。删除被运行/历史实例引用的版本应明确拒绝。
2. 节点字段规则绑定 definitionId/taskDefinitionKey/formVersionId，服务端从实际任务推导，不能采信客户端传来的节点、角色或表单版本。
3. 原始历史数据只通过有权限的接口读取。合并写入仅允许该节点可写字段；隐藏字段既不下发也不接受回写。多角色规则需明确定义冲突优先级并测试，不能取到任意一条权限就通过。
4. 优先修复/补齐现有表单包装，确认实际依赖许可证、版本和 Vue 兼容性；不要把一个无法注册的自定义标签当作完成的表单渲染器。前后端采用同一受支持字段/校验子集；未知组件或执行脚本需明确报错。
5. BPMN 部署继续由服务器校验：XML 大小及结构、可执行 process key、节点/表达式/Delegate 白名单、候选身份来源、路径完整性和必要异步边界。设计器只暴露已实现、可执行的属性，不通过任意 Java 类名或脚本获得服务器执行能力。
6. 设计器依赖通过 package.json/package-lock 固定，使用独立懒加载页；保留手工 XML 导入/导出。实际演示至少覆盖可编辑图、属性保存、部署校验错误及发布后运行，不能用静态截图替代交互。
